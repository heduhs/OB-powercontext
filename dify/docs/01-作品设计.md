# 《读心酒馆》作品设计

> 一句话:城南有家小酒馆,酒保老周不会读心,他只是记性好。
> 你在心里想一个东西,他只问"是 / 不是";而你玩过的每一局,都被他记在那本赊账本上。

## 1. 为什么是这个点子

派对上最好用的 AI 演示是一个**赌局**:AI 能不能猜中我心里想的东西。
经典"20 个问题"玩到第三盘就露馅——AI 每次都从零开始,问一模一样的傻问题。

本作把"记忆"从装饰改成了**胜负条件**:

- 老周每局结束会把"你偏什么类别、你怎么答话、他自己是第几问猜中的"写进 PowerContext;
- 下一局开局,他先翻账本,直接跳过你历史上必答的问题;
- 于是出现一个可量化的反转:**同一个玩家,老周用得越来越少的问题就猜中了他**。

趣味钩子(全部由记忆驱动,不是写死的台词):

| 钩子 | 玩家看到的效果 |
| --- | --- |
| 翻旧账 | 一进门:"又来了?上回你想「苹果」让我问了 9 个破问题。" |
| 越玩越准 | 实测同一玩家 10 问 → 6 问 → 6 问,老周会自己报进度 |
| 赊账本 | 老周猜错要"记一笔自嘲",下次见面自己念出来 |
| 生面孔 | 账本为空时,老周的态度明显不同:"头一回见,咱们从头认识。" |
| 私人梗 | 你反复用"看情况"赖皮,老周会把你这条习惯记下来并在后面拿它开涮 |

## 2. 玩法闭环

```
进门报名 → 开局(心里想一个名词) → 老周每轮问一个是/否问题
        ↑                                        ↓
        │                              玩家答:是/不是/看情况/不知道
        │                                        ↓
   翻账本(召回记忆) ←──── 下一局 ──── 老周下注(3 候选 + 1 押注)
                                                ↓
                                   玩家判定:猜中了 / 没猜中
                                                ↓
                                   结算并记账(写入记忆)
```

规则(写进主持人系统提示,模型必须遵守):

1. 玩家在心里想一个**具体名词**,限定 6 大类:食物 / 动物 / 物品 / 地点 / 人物 / 虚构。
2. 玩家回答只用:`是` `不是` `看情况` `不知道` `跳过`。
3. 老周每轮**只问一个**是/否问题,一次最多 12 问。
4. 第 5 问起允许"试探性下注";第 12 问必须下最终注:给 3 个候选并明确押 1 个。
5. 玩家判定命中后,本局结算;老周当轮给出总结 + 一句自嘲或挑衅,并邀请下一局。
6. 中途不想玩了可以说"换人"或"重来",老周会先结算再开新局。

## 3. 角色与文案

**老周**(酒保):慢热、爱面子、算得清账。说话短,不解释自己怎么猜的,只在下注时亮一次思路。
台词风格样例(实际输出由模型现场生成,不由脚本写死):

- 生面孔:"新客?规矩简单:你想一个,我问,你答。我不猜,我等。"
- 熟客进门:"老张。你上回连开三局都想吃的,这次不换类别我当场把抹布吃了。"
- 下注:"三个:锅贴、烧麦、苹果。我押苹果——你上回对『能剥皮吗』答是,这回也答是。"
- 输了:"没中。这一笔我记下,下回你输得会更难看。"
- 赢了:"第三问。比你上回少了六问,不是我变聪明,是我记得你。"

## 4. 记忆契约(本作品的技术核心)

一个玩家 = 一个 PowerContext `scope`。Dify 侧用 `integration=dify / kind=player / external_id=<玩家名>`
的 scope binding 做映射,所以**换一个 Dify 会话、换一个浏览器,只要报名同一个名字,老周仍然认得**。

| 记忆 kind | 何时写 | 内容 | 何时读 |
| --- | --- | --- | --- |
| `round-record` | 每局结算 | 局号、类别、答案、问题数、是否命中 | 开局翻账本 |
| `player-preference` | 累计 2 局同类别后 | "老张 4 局里 3 局想食物" | 开局,决定首问与先验 |
| `answer-pattern` | 结算 | "对『有生命吗』必答是""爱用『看情况』赖皮" | 提问中,跳过必答问题 |
| `bartender-self-note` | 猜错时 | 老周的自嘲一笔 | 下次见面自己念出来 |

读的一侧统一走 `POST /v1/context/prepare`(带字节预算),拿到的是一段有界的 Markdown 上下文包,
直接拼进主持人 system prompt;`status=empty`(新客)与 `status=ready`(熟客)在玩法上是两种开场,
这正是"记忆真的在起作用"的分岔口。

## 5. 为什么必须是 PowerContext(而不是 Dify 自带记忆)

| 需求 | Dify 会话变量 | PowerContext |
| --- | --- | --- |
| 本局第几问、当前类别、进行中状态 | ✅ 天然够用(同一会话内) | 不需要 |
| 换一个会话 / 换设备后还认得老张 | ❌ 会话变量随会话销毁 | ✅ scope binding 按玩家名持久 |
| 有界上下文注入、按相关性召回、字节预算 | ❌ 全量拼历史 | ✅ `context/prepare` 的 max_bytes |
| 逐条审计"老周到底记了我什么" | ❌ 黑盒 | ✅ `memory/entries/list` 可查可证 |

所以分工是:**Dify 管编排与局内状态,PowerContext 管跨会话的"人"的记忆**。两者都是必需的,
不是把 PowerContext 当装饰库。

## 6. 验收时看什么

1. 导入 `app/mindtavern_chatflow.yml`,配置模型与 `PC_BASE_URL` / `PC_TOKEN` 后能对话。
2. 同一玩家名跨两个 Dify 会话:第二个会话开场就cue第一个会话的局数与答案。
3. 同一玩家连打多局:`evidence/run-logs/dify-final.md` 记录每局问题数(实测 10 → 6 → 6),
   以及每局开局如何引用上一局的类别、局号与问题数。
4. 换一个玩家名:开场变回生面孔(记忆召回 `status=empty`),不会串号。
5. Dify 运行日志里 HTTP 节点对 PowerContext 的 `context/prepare`、`memory/remember` 请求可见,
   且 PowerContext 侧 `memory/entries/list` 能查出对应记录。
