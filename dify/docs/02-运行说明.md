# 运行说明

本作品由两部分组成:**Dify Chatflow(编排)** + **PowerContext Server(记忆)**。
两者通过 HTTP API 相连,除模型密钥外没有其他外部依赖。

## 1. 版本与环境

| 组件 | 本作品验证所用版本 | 备注 |
| --- | --- | --- |
| Dify | **Dify Cloud(控制台自报 1.17.1)**,DSL `version: "0.7.0"` | Chatflow(advanced-chat)。本作品在云端真实导入并跑通 |
| PowerContext | master 分支 commit `927bb6e`,包版本 `0.1.dev1+g927bb6ee1`,HTTP API contract `1.4` | 用 `pip` 直接安装,无需 Docker |
| Python | 3.12.10(PowerContext 要求 `>=3.11,<4.0`) | Windows / Linux / macOS 皆可 |
| 存储后端 | SQLite + `sqlite-vec`(默认) | 同一套 DSL 不改,可切 `seekdb` / `oceanbase`,见第 6 节 |
| 模型 | MiniMax 插件 `langgenius/minimax:0.0.29`,模型 `minimax-m3.1-flash`(区域 `https://api.minimaxi.com/v1`) | DSL 默认即此模型;换成你工作区里任意已配置的对话模型都行 |
| Embedding / Rerank | **不需要** | 不配推理与向量模型时,PowerContext 走 FTS 全文召回,本作品的记忆链路照样成立 |
| 资源 | PowerContext 约 200 MB 内存;Dify 自建按官方建议 ≥2C4G | 记忆服务与 Dify 不必同机 |

配置示例一律用占位值:`<PC_TOKEN>`、`<MINIMAX_API_KEY>`。请把这些放进环境变量或 Dify 的
secret 型环境变量,**不要写进 DSL,也不要提交进仓库**。

## 2. 起记忆服务(PowerContext)

### Windows(本次实测路径,无 Docker)

```powershell
cd dify
.\scripts\run_powercontext.ps1
```

脚本会:建 `.venv-powercontext` → `pip install "powercontext[cli,server] @ git+https://github.com/oceanbase/powercontext.git@master"`
→ 生成 Bearer 令牌写入 `dify/PC_TOKEN.txt` → 以 `ACCESS_MODE=enforced`、`DATABASE_KIND=sqlite` 启动,监听 `127.0.0.1:8100`。
它自己会打印下一步该填进 Dify 的两个值。

### Linux / macOS

```bash
python -m venv .venv && . .venv/bin/activate
pip install "powercontext[cli,server] @ git+https://github.com/oceanbase/powercontext.git@master"
export POWERCONTEXT_HOME="$PWD/.pc-data"
export POWERCONTEXT_SERVER_ACCESS_MODE=enforced
export POWERCONTEXT_SERVER_AUTH_TOKEN='<PC_TOKEN>'
export POWERCONTEXT_SERVER_DATABASE_KIND=sqlite
powercontext server run
```

已经 clone 过 powercontext 仓库的话,可改用本地安装:`pip install -e "<powercontext 路径>[cli,server]"`。

### 自检

```bash
export PC_BASE_URL=http://127.0.0.1:8100
export PC_TOKEN='<PC_TOKEN>'
python scripts/smoke_test_powercontext.py
```

9 项断言(建区幂等、写入、召回 `ready`、检索、审计列表、新玩家 `empty` 隔离等)全 PASS 才继续。

## 3. 导入 DSL

1. Dify 工作区 → **创建应用程序 → 导入 DSL 文件**,选择 `app/mindtavern_chatflow.yml`。
2. 导入后进入 **编排** 页面,依次处理三处必改项:
   - **环境变量**(右上角"环境变数"面板):
     - `PC_BASE_URL` = 记忆服务地址。自建 Dify 在容器里访问宿主机:`http://host.docker.internal:8100`;
       同机部署用 `http://127.0.0.1:8100`;Dify Cloud 用公网地址(见第 5 节)。
     - `PC_TOKEN` = `<PC_TOKEN>`,类型选 **secret**。
   - **LLM 节点「老周主持」**:DSL 默认写的是 `langgenius/minimax/minimax` + `minimax-m3.1-flash`
     (本次实测所用)。若你的工作区没装 MiniMax 插件,导入后该节点会显示模型不可用 ——
     在节点里改选你已配置的任意对话模型即可(推荐指令跟随稳、输出简短的型号;
     实测 `MiniMax-M3.1-Flash` 与 `gpt-4.1` 都能稳定遵守"一轮只问一个问题 + 末尾 STATUS 协议行")。
   - 三个 HTTP 节点(`取玩家的 scope` / `翻账本` / `写入记忆`)无需改动,鉴权头与地址都走环境变量。
3. 右上角 **运行** → 调试面板里发一句「开局」→ 无红叉后 **发布**。

知识库、工具、插件均**不需要**:记忆走 DSL 内的 HTTP Request 节点直连 PowerContext
(赛题允许该接入方式)。PowerContext 仓库自带的官方 Dify 插件 `integrations/dify/plugin`
是等价的另一条路,但它需要额外装 `.difypkg`、要求管理员预置 scope 绑定,可复现性更差,
本作品不采用;需要插件时按该目录 README 配置 `server_url` / `api_token` / `scope_id` 即可。

## 4. 应用入口与玩法

- 入口:发布后的 **WebApp 对话页**(或 `/v1/chat-messages` API,`inputs` 可为空)。
- 开场会给建议问题:「开局」「我想好了」「我这人有什么毛病」「直接下注」。
- 你只需:先说「开局」并在心里定一个名词;之后每轮只回 **是 / 不是 / 看情况 / 不知道 / 跳过**;
  老周下注后你回「猜中了」或「没猜中,其实我想的是××」。
- 结算那轮,回复末尾会多一行 `📔 老周翻开账本记了一笔…`,那是记忆写入成功的回执。

## 5. Dify Cloud 的额外一步:让云端能访问本机记忆服务

Dify Cloud 的 HTTP 节点在云端执行,访问不到你的 `127.0.0.1`。演示时我们用一条临时公网隧道:

```bash
cloudflared tunnel --url http://127.0.0.1:8100     # 输出一个 https://xxx.trycloudflare.com
```

把该地址填进 `PC_BASE_URL`。因为服务以 `ACCESS_MODE=enforced` 启动,公网侧必须带 Bearer 令牌
(`/v1/*` 无令牌返回 401,已验证);`/health/*` 是服务自己的免鉴权探针。
隧道地址每次重启都会变,它只是演示链路,**不是交付依赖**:评审自建 Dify 时用 `host.docker.internal`
或局域网地址即可,不经过任何第三方隧道。

## 6. 可选升级:把 PowerContext 的存储换成 seekdb

本作品的达标口径是"实际使用 PowerContext",不依赖 seekdb。若想在同一套 DSL 上再加 seekdb,
只需换 PowerContext 的存储后端(Dify 侧零改动):

```bash
export POWERCONTEXT_SERVER_DATABASE_KIND=seekdb
export POWERCONTEXT_SERVER_SEEKDB_ENDPOINT='<host:port>'   # 具体变量见 PowerContext 配置文档
```

此时分工变成:**seekdb 承载 PowerContext 的记忆/向量存储与检索,Dify 负责编排与局内状态**。
注意 `pylibseekdb` 的嵌入式模式在 Windows 不可用(依赖标记仅 linux/darwin),需 seekdb 服务端或 Linux 环境。

## 7. 已知限制

1. **无向量模型时靠全文检索召回。** 记忆条目里刻意带 `读心酒馆|战绩|第N局|类别=…|问题数=…` 这类
   固定词,DSL 用"固定探针词 + 玩家本轮原话"作为 `query`,保证 FTS 稳定命中。若给 PowerContext
   配上 embedding,`mode=auto` 会自动升级为混合检索,DSL 不用改。
2. **记忆写入不去重。** `/v1/memory/remember` 是追加语义,同一句话重复写会产生多条。
   DSL 每个结算轮只写一条、且文本里带局号,自然不重复。
3. **玩家身份取 `sys.user_id`。** 在 Dify 调试预览面板里,它可能是当前调试用户;取不到时回落到
   `conversation_id`(此时记忆只在会话内连续,跨会话演示请用 WebApp 或 API 指定 `user`)。
   `docs/03-验证样例.md` 的样例 1 用同一 `user` 换会话的方式验证跨会话记忆,不受这条影响。
4. **HTTP 节点的降级边界。** 记忆服务"应答但异常"(401/4xx/5xx)会走 DSL 的降级分支,老周说
   "账本忘带了"、酒馆照常营业;服务完全连不上时,Dify 会让该节点报错——这是 Dify HTTP 节点的固有行为。
5. **问题数依赖模型的 `state` 标注。** 计数由代码节点算好再写回(不让模型自己数数),
   但"这一轮算不算问了一问 / 是不是新开一局"取自模型输出的 `state`;模型连续自判 `open`
   本会把计数抹掉,DSL 用 `reset_count`(仅在本局确实还没开始时才归零)兜住了这个情况。
6. 台词与观察由模型现场生成,同一输入不保证逐字复现;验收看的是规则与记忆链路,不是唯一答案。
7. **记忆会形成先验,跨类别时会先踩空一次。** 实测:玩家连续几局想食物后,老周开局会先问"是食物吗";
   若这一局改想地点,第一问就会落空。这是"越玩越准"的另一面,属于玩法特性(老周自己也会说"这回不混上一局"),
   不是记忆读错 —— 读到的内容与账本一致。

## 8. 会话变量的写法有坑(已在交付 DSL 中规避)

实测:数字型会话变量若写成 `value_type: number`,Dify **导入时不会**像控制台接口那样把它规范化成
`integer`,运行时会在**初始化阶段直接 500、一个节点都不执行**——现象极难定位(不报变量名,也没有节点日志)。

本 DSL 的规避做法有两条,复用时请一并保留:

1. 所有计数类会话变量(`round_no` / `asked_count`)声明为 `string`,自增在代码节点里用 `int()`
   算完再写回;
2. 会话变量与环境变量的 `id` 一律用 UUID(Dify 自己导出的格式)。

`tools/validate_dsl.py` 会对 `value_type: number` 直接报错并解释这个现象,避免再踩。
