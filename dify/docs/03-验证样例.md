# 验证样例与运行证据

三组样例都可按步骤重放。执行顺序有要求的会写明,末尾给恢复初始状态的方法。
环境准备见 `02-运行说明.md`;下面的 `<user>` 指 Dify 传给应用的终端用户标识(API 调用里的 `user` 字段)。

---

## 样例 1 · 跨会话记忆:换个会话进来,老周还认得你

**验证的能力**:PowerContext 承担"人"的长期记忆(Dify 会话变量做不到)。

**前置**:记忆服务已启动且 `smoke_test_powercontext.py` 全绿;Dify 应用已发布;`PC_BASE_URL`/`PC_TOKEN` 已配好。

**步骤**

1. 以 `<user>=zhang-03` 开会话 A,发「开局」→ 心里想一个词(例如"苹果")→ 按是/否回答若干轮
   → 老周下注 → 回「猜中了,我想的是苹果」。
2. 同 `<user>` 开会话 B(Dify WebApp 点"新对话",或 API 不带 `conversation_id` 新建),发「开局」。

**预期**

- 会话 A 结算轮:回复末尾出现 `📔 老周翻开账本记了一笔:第1局,7 个问题,入账 1 条`。
- 会话 B 开场:老周**主动提到会话 A 的具体旧事**(第几局、什么类别、几个问题、中没中),
  并且第一个问题就避开账本里"必答是"的方向 —— 回复状态应为 `ready` 而非 `empty`。

**证据**(逐条可核,均在 `evidence/` 下)

- `run-logs/dify-final.md`:结算轮的回复带 `📔 老周翻开账本记了一笔:第N局,X 个问题,入账 1 条`。
- `memory/zhang-03.md`:该玩家的全部记忆,每条 `round-record` 正文含局号/类别/答案/问题数/命中/观察,
  末尾附"注入给模型的上下文包"(即 `context/prepare` 的真实返回)。
- `memory/xiaow-empty.md`:另一身份的对照 —— 0 条记忆、召回状态 `empty`。
- `powercontext-access.log`:服务端操作日志,`create_scope` / `prepare_context` / `remember_memory`
  的 operation、outcome、status_code、耗时逐条可查。
- 界面复核(评审如需):在 Dify 应用 **日志** 页打开结算轮的运行详情,
  `取玩家的 scope`、`翻账本`、`写入记忆` 三个 HTTP 节点的请求/响应与上面 JSON 一一对应。

## 样例 2 · 记忆的收益可量化:越玩越准

**验证的能力**:召回的记忆真的改变了模型行为,而不只是"读出来了"。

**步骤**(同一 `<user>`,连打 4 局,每局都开新会话 —— 直接用交付脚本)

```bash
set DIFY_API_KEY=app-xxxx            # 应用的 API 密钥(访问 API 页生成)
python scripts/run_dify_evidence.py --user zhang-03 --rounds 4 --max-turns 14 ^
       --out evidence/run-logs/dify-final
```

脚本里的"玩家"是**确定性**的:每个候选词带一张属性表(是否食物/有生命/水果/甜/人造/电子/地点/人物/虚构…),
按老周最后一句提问查表回答,所以同一份 DSL 可以被任何人重放出同样的走势。

**预期**

- 控制台末尾打印「每局问题数」,并写出 `evidence/run-logs/dify-final.json` / `.md`。
  本次实测:第 1 局 10 问 → 第 2 局 6 问 → 第 3 局 6 问(第 4 局因脚本玩家的属性表覆盖不到"地点"
  而答不出是/否,撞到轮次上限未结算 —— 属采集脚本限制,不是应用缺陷,已在 `02` 第 7 节说明)。
- `.md` 里每局都有:玩家每轮原话、老周每轮回复、会话 ID;结算轮的回复带 `📔 …入账 1 条`。
- 第 2 局起,老周的开场会引用上一局的具体旧事(见样例 1),并跳过账本里"必答是"的方向。

**没有 Dify 实例时的等价路径**(逐节点执行 DSL 本体,同一份代码与提示词):

```bash
set LLM_API_KEY=<你的 OpenAI 兼容密钥>
python tools/dsl_replay.py --autolive rounds=4 --user zhang-03 --out evidence/run-logs/autolive
```

**说明**:本作品的曲线证据以 `evidence/run-logs/dify-final.md`(真实 Dify 实例内产生)为准;
回放器用于让没有 Dify 环境的评审也能完整体验玩法并复算同一指标。

## 样例 3 · 玩家隔离:换个名字就是生面孔

**验证的能力**:记忆按玩家分区,不会串号;`empty` 与 `ready` 是真实分岔。

**步骤**

1. 完成样例 1(或样例 2)使 `<user>=zhang-03` 有记忆。
2. 用 `<user>=xiaow`(新身份)开会话,发「开局」。
3. `python scripts/dump_memory.py --user xiaow` 与 `--user zhang-03` 各跑一次。

**预期**

- `xiaow`:开场是生面孔口径(自我介绍 + 讲规矩),`dump_memory` 显示 `记忆条数 = 0`、`召回状态 = empty`;
  **不会**出现 zhang-03 的任何旧事。
- `zhang-03`:仍能看到自己那几条战绩,`召回状态 = ready`。
- 服务端审计:xiaow 的 `翻账本` 响应是 `status=empty, content=null`,zhang-03 的不是。

## 样例 4 · 降级:记忆服务异常时不崩

**步骤**:把 Dify 环境变量 `PC_TOKEN` 改成一个错值(或停掉记忆服务后重启服务但用旧令牌),发一句「开局」。

**预期**

- 令牌错(401):`取玩家的 scope` 拿到非 2xx → `解析 scope` 输出空 → 走 `拿到账本了吗` 的 false 分支 →
  `没带账本` → 老周仍然正常开场,口径是"账本忘带了 / 咱们从头认识"。回复不应包含任何旧事。
- 服务完全连不上:Dify 的 HTTP 节点报错(这是 Dify HTTP 节点的固有行为),`docs/02` 第 7 节第 4 条已说明。

**恢复**:把 `PC_TOKEN` 改回正确值即可,无需重置数据。

---

## 恢复初始状态

1. **换一个 `<user>` 标识**即可得到全新的"生面孔"状态(推荐,不影响历史证据)。
2. 或清空记忆库:停止 PowerContext 服务 → 删除 `dify/.pc-data/`(或 `POWERCONTEXT_HOME` 指向的目录)
   → 重跑 `scripts/run_powercontext.ps1`。
3. 回放器的会话状态在 `dify/.replay-state/*.json`,删掉即回到"Dify 侧新会话"的初始态
   (注意:这只重置局内状态,PowerContext 里的长期记忆仍按 `<user>` 保留 —— 这正是两者分工的体现)。
