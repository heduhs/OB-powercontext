# 指标定义与调参方法

## 二元相关下的四个指标

设某条查询标注的相关文档集合为 `R`（`|R| = n`），系统返回的有序结果为 `D`。

| 指标 | 定义 | 看什么 |
|---|---|---|
| recall@k | `|top-k(D) ∩ R| / n` | **取全能力**。RAG 最重要的一个：该给模型的上下文没召回，生成就无从谈起 |
| precision@k | `|top-k(D) ∩ R| / k` | 噪声率。k 固定时与 recall@k 同向，但 n < k 时会被稀释 |
| MRR | `1/rank(第一个命中的相关文档)`，对所有查询取均值 | 用户只看第一条时的体验 |
| nDCG@10 | `DCG@10 / IDCG@10`，相关文档增益为 1，位置折扣 `1/log2(pos+1)` | 头部排序质量，兼顾取全与排序 |

实现见 `scripts/metrics.py`。两个刻意的实现选择：

1. **未标注的查询（`R` 为空）不参与平均**，返回 `None` 并被跳过。把“没标注”当成“全错”会让指标虚假地低。
2. **nDCG 的 IDCG 用 `min(|R|, k)` 计算**，因此只标了 1 篇的查询最多也只能拿 1.0 —— 标注不全时 nDCG 会被系统性推高，这也是要求“该命中的都标上”的原因。

`empty_result_rate` 不是标准指标，是本技能加的诊断量：**某条腿返回空结果的查询占比**。中文分词器缺失这类静默故障，靠它一眼看穿。

## 该优化哪个指标

- 给大模型喂上下文的 RAG：先 `recall@k`（k 取你实际塞进 prompt 的篇数），MRR 其次。
- 搜索框 / 客服首条命中：MRR 和 `recall@1` 优先，precision@k 兜住噪声。
- 只要“别漏”的合规/审计场景：`recall@k` 单一目标，接受 precision 下降。

单一数字会骗人。**同一份标注上并排看 recall 与 MRR**，两者最佳权重不一致是常态（示例集上 recall 峰在 `w_vec=0.3`，MRR 峰在 `w_vec=0.7`），这说明两条腿的相对贡献在头部和尾部不同。

## 调参顺序与旋钮

```
链路正确性 → embedding → 索引/查询参数 → 分词与数据 → 融合权重 → 重排
```

| 旋钮 | 位置 | 作用 | 什么时候动 |
|---|---|---|---|
| embedding 模型 | `--backend api --model` / `--backend seekdb --model` | 语义泛化上限 | 第一个该动的东西，别先用 `local` 下结论 |
| `@@ob_hnsw_ef_search` | 会话变量，默认 64 | 检索期候选宽度，召回↔耗时 | recall 不足但确认走了索引之后 |
| `M` / `EF_CONSTRUCTION` | 建索引 `WITH (...)` | 图质量、内存与构建时间 | 索引构建成本可承受时提高 |
| `--depth` | 每条召回腿取回条数 | 融合能看见多少尾部 | 必须 ≥ `--k`；小语料上常常无信号 |
| `--rrf-k0` | RRF 分母常数，默认 60 | 越小越偏头部 | 头部压太狠时调大 |
| `--w-vec` | 向量腿权重（全文腿 = 1-它） | 两腿话语权 | 用扫描定位，别猜 |
| 自定义词典 / `ft_stopword_file` | 全文侧 | 专有名词、同义词召回 | 全文腿单独差时 |
| 切块粒度 | 语料预处理 | 语义完整性 | 答案跨块时 |

## 扫描怎么做才有意义

```bash
# 权重扫描（其余参数固定）
for w in 0.0 0.2 0.4 0.5 0.6 0.8 1.0; do
  python scripts/evaluate.py --qrels q.jsonl --table T \
    --strategies vector,fulltext,hybrid_weighted --w-vec "$w" --out "sweep/w_$w" >/dev/null
done

# 深度扫描
for d in 10 30 50 100 200; do
  python scripts/evaluate.py --qrels q.jsonl --table T --depth "$d" --out "sweep/d_$d" >/dev/null
done
```

三条纪律：

1. **一次只动一个变量**，其余全部固定，并把命令行留在报告里（`report.json` 的 `args` 字段自动记录）。
2. **端点最优不是调参成功**：`w_vec=0` 或 `1.0` 最优意味着另一条腿此刻无信息，回去修链路。
3. **样本量诚实**：几十条查询里 1~2 个点的差异基本是噪声（示例集 16 条查询、`n_relevant` 合计 23 篇，1 篇的得失就是 0.043）。要写进结论的数字，至少上百条查询、上千篇文档，并注明语料规模与标注方式。

## 融合为什么默认用 RRF

余弦距离与 BM25 分数量纲不同，加权求和必须先归一化（本技能 `weighted` 用 min-max），而 min-max 的端点随候选集变化，跨查询不可比；RRF 只用名次，对分布不敏感，因此更稳，也是默认建议。代价是丢掉了“相关度差多少”的信息 —— 所以两种都实现了，让数字说话。

## 想把融合搬进一条 SQL

见 `references/sql-patterns.md` 第 6 节：两个 CTE 出 `row_number()`，`union all` 后按 `sum(w/(k0+rn))` 聚合排序。客户端融合的余处是同一份标注下可以顺便做指标、漏召清单和权重扫描，SQL 版本则适合线上少一次往返的路径。
