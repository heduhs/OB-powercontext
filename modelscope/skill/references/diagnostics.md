# 诊断手册：指标异常 → 根因 → 验证 → 动作

按“先确认链路，再怀疑算法”的顺序排。每条给出可复现的验证手段，`evaluate.py` 已把其中能自动化的部分实现成了诊断输出。

---

## A. 全文腿几乎不返回结果，向量腿正常

**根因优先级**

1. 建索引时没有 `with parser ik`（中文场景 90% 是这个）。默认按空格切词时，一整句中文被当成一个词，`against('向量检索')` 永远不相等 → 空结果，**且不报错**。
2. 写入时连接没带 `charset=utf8mb4`，中文落库已成乱码。
3. 全文索引根本没建上（只建了向量索引）。

**验证**

```sql
show index from T;                                   -- 有没有 FULLTEXT 这一行
select doc_id from T where match(body) against('MySQL') limit 1;  -- 英文能命中说明索引在，中文不行说明是分词器
select doc_id, body from T limit 1;                   -- 肉眼看是否乱码
```

**动作**：`python scripts/build_index.py --corpus c.jsonl --table T --parser ik`（默认就是 ik，重建会 drop 表）。

**量化参考**：示例语料下，ik 与默认分词器的全文腿对比是 recall@10 `0.8542 → 0.3021`，空结果率 `0.0 → 0.5625`。

---

## B. 向量腿 recall 明显低于全文腿

**根因**

1. embedding 后端本身是词法的（本技能的 `local` 后端就是字符 n-gram 哈希，故意做成这样用于离线自检）。
2. 查询向量与文档向量来自不同模型 / 不同维度，距离值域对不上。
3. 切块把语义切断了：答案跨块，任何 embedding 都救不回来。

**验证**：`--backend api` 换真实模型重跑同一份标注；如果差距收敛，就是 1；没变化，查 2 和 3。

**动作**：换语义 embedding；跨段落答案改小块召回 + 邻居拼接（`title` 拼进 embedding 文本通常能带来几个点的提升，本技能默认 `title。body` 拼接）。

---

## C. 加了 `--filter` 之后所有策略一起变差

**这不是检索变差，是指标上限被压死。** 过滤把标注里的一半相关文档排除在候选之外，recall 就永远拿不到那部分分。

`evaluate.py` 会显式算出来：

```
标量过滤 category=hybrid 使标注文档只有 47% 落在过滤范围内，这就是本轮 recall 的上限
```

**正确姿势**：让过滤值与查询子集一致 —— `--filter category=hybrid --only-tag hybrid`，此时示例集 recall@10 = 1.0000。

**顺带检查**：过滤与近似索引的执行顺序。过滤率很高（例如多租户只放行 1%）时，`where` + `approx` 可能取不满 k 条，需要加大 `--depth` 或改成先过滤再取近邻的两步写法。

---

## D. 结果看着对，但数据量一大就慢

**根因**：`approx` 漏写，或查询距离与索引 `WITH (distance=...)` 不一致，导致优化器没走向量索引。

**验证**

```sql
explain select doc_id from T order by cosine_distance(embedding,'[...]') approx limit 3;
-- 期望：VECTOR INDEX SCAN T(vidx)
-- 退化：TABLE FULL SCAN
```

再用 `select @@ob_hnsw_ef_search;`（默认 64）确认检索期候选宽度。

---

## E. 头部命中很准，但取不全（recall@1 高、recall@10 上不去）

**根因**：候选池 `--depth` 太小，融合阶段看不见第二名之后的相关文档；或者 `--rrf-k0` 太小让头部噪声压制了尾部。

**验证**：`--depth 10` / `--depth 100` 各跑一次同一份标注，看 `hybrid_*` 两行是否随之上升。

**注意（实测边界）**：小语料上 depth 常常没影响 —— 示例集 36 篇文档、k=10 时，depth 10/20/50/100 的向量腿 recall@10 恒为 0.8021，混合腿在 0.8854~0.8958 之间抖动。**语料上千篇之后再谈候选池调优才有信号**，小样本上的差异多半是噪声，不要拿去写结论。

---

## F. 换个模型指标却几乎没动

多半是**标注集太宽容或太严格**：

- 只标第一篇 → 真正相关的结果被算成错，任何模型都上不去；
- 把“沾边就算对”全标上 → 区分度消失，换模型看不出差别。

**动作**：按四类查询（同义改写 / 专有名词 / 口语化 / 跨类目歧义）重做 20~30 条标注，并保留 `tags` 便于分组看指标。

---

## G. 融合权重扫描出来是端点最优（a=0 或 a=1）

说明另一条腿此刻没有信息增量，调权重救不了。回到 A/B/D 修链路。健康的形态是**内部最优**：示例集上 `w_vec=0.3` 拿到 recall@10 峰值 0.9167，高于纯全文 0.8542 与纯向量 0.8021。

另一个信号：如果 recall 峰值和 MRR 峰值出现在不同权重（示例集 MRR 峰值在 0.7），说明“取全”和“第一条就对”在打架 —— 先定业务目标再选权重，别只看一个指标。

---

## H. 写入阶段就失败

| 报错形态 | 原因 | 动作 |
|---|---|---|
| 维度不匹配 / 写入被拒 | 向量维度 ≠ `vector(N)` | 统一模型，重建表 |
| 中文变成乱码 | 连接未指定 `charset=utf8mb4` | 连接参数补上 |
| 建索引时连接被重置 | 在已有全文索引的表上单独补建向量索引 | 两种索引写在同一条 `CREATE TABLE`（本技能默认如此） |
| 磁盘被日志写满 | 默认日志级别刷盘太快 | 启动加 `--log-level=WARN` |

## 报告怎么读

`report.json` 里每条查询都留了证据，排查具体 miss 时够用：

```json
{"query_id":"q02","query":"中文全文检索查不到东西","n_relevant":2,
 "hybrid_weighted":{"top":["d31","d13","..."],"found@k":2,
                    "missed":[],"first_rank":1}}
```

- `first_rank`：第一个相关文档出现在第几名。`null` = 在 depth 范围内完全没召回 → 补语料/改切块。
- `missed`：前 k 名里缺席的相关文档 → 通常指向分词或权重。
- `empty_result_rate`：某条腿的空结果率，A 类问题的直接读数。
