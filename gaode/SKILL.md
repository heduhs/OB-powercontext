# 周边去哪儿：基于高德的地点推荐助手

## 0. 最短执行路径（先照这 6 步做，细节见对应章节）

1. 定起点坐标：已给就用（校验经纬度顺序），只给地名就 `maps_geo` → §2.1
2. 定参数：类型词、步行上限分钟、最多 3 条、排序偏好 → §2
3. `maps_around_search(location, keywords, radius=max(1000, 上限×80×1.5))` 拿候选 `id` → §3
4. 对候选逐个 `maps_search_detail(id)` 补 `location`、校验 `type` 类别，按直线距离宽松留最近 6 个 → §4
5. 对这 6 个逐个 `maps_direction_walking(origin, destination)` 取 `paths[0].distance`/`duration` → §5
6. 剔除超时与类别不符 → 合并子部件与同品牌多店 → 按步行耗时升序 → 取前 3 → 出表格 → §6

跑不通就如实说，**永远不要编造地点、坐标、距离或时间**。

## 1. 用途与适用场景

帮用户用一句话找到合适的地点，并知道怎么走到达。

适用：用户给出 **城市 + 起点 + 自然语言需求**，想找起点周边的咖啡馆、餐厅、公园、书店、便利店等某一类地点，并需要步行到达信息。

不适用（明确拒绝并说明原因）：多点行程串联、驾车/打车/公交通勤规划、跨城市对比、需要实时营业/排队/人流等高德不提供的内容。

**本技能为单轮任务**：一次对话内直接完成"理解需求 → 查询高德 → 返回推荐"，**不要向用户追问**。缺少的信息用第 2 节的默认值补齐，并在回答里用一行说明所用假设。

各推荐地点都是从**同一个起点**出发的**独立备选**，不要串成多站行程。

## 2. 第一步：把需求解析成结构化条件

从用户输入中抽取以下字段，逐项落到具体数值：

| 字段 | 说明 | 缺失时的默认值 |
| --- | --- | --- |
| `city` | 城市名，如"杭州" | 从起点地名推断；无法推断则留空 |
| `origin_coord` | 起点坐标，高德格式 **`经度,纬度`**（GCJ-02） | 必须获得，见 2.1 |
| `poi_need` | 地点类型关键词，如"咖啡馆""公园""面馆" | 无默认；确实无法判断时按"餐饮"处理并声明 |
| `walk_limit_min` | 可接受的**步行**时间上限（分钟） | 20 分钟，并在回答中声明 |
| `top_n` | 推荐数量 | `min(3, 用户指定值)`，**任何情况下不超过 3** |
| `order_pref` | 偏好排序，如"优先近一点""评分高优先" | 默认"近优先"（按步行耗时升序） |
| `extra` | 其它约束（预算、人均、是否要商圈、避开连锁等） | 无 |

**2.1 起点坐标**

- 若输入已给出坐标，直接使用。**先做合理性校验**：中国范围内经度在 73~135、纬度在 3~54。若发现形如"小值,大值"（如 `30.28,120.12`），说明是"纬度,经度"顺序，必须换算成高德要求的 `经度,纬度` 再使用——用反了会查到另一个城市。
- 若只给出起点名称（如"某某地铁站"），调用 **`maps_geo`**（`address`=起点名称，`city`=城市）取得坐标；返回多条时选与起点名称最匹配的一条。
- 若需要确认起点是什么地方，可调用 **`maps_regeocode`**（`location`=坐标）。
- 拿不到可靠起点坐标时，**不要猜测、不要用市中心坐标蒙**，直接如实说明"起点无法定位，无法给出可信的步行推荐"，并建议用户补充更具体的地点名或坐标。

**2.2 把步行时间上限换算成搜索半径**

搜索半径按预算换算，但**必须取 1000 米的下限兜底**：

```
radius(米) = max(1000, round(walk_limit_min × 80 × 1.5))
例：15 分钟 → max(1000, 1800) = 1800
    2 分钟  → max(1000, 240)  = 1000     ← 不要用 240，会查空
```

**为什么要有下限**：实测证明半径过小会让周边搜索直接返回空列表——同一批公园候选，`radius=240` 返回 **0 条**，`radius=2400` 返回 20 条。半径只负责"把候选捞出来"，**超时与否一律交给 §5 的路线结果判定**，所以宁可捞宽一点。

半径只用于**粗筛候选**，绝不能当作步行结果。**是否满足时间上限，只能由 §5 的步行路径规划返回值判定。**

## 3. 第二步：查询候选地点（高德周边搜索）

主用工具 **`maps_around_search`**（周边搜索）：

```
maps_around_search(
  location = origin_coord,        // 必填，"经度,纬度"
  keywords = poi_need,            // 如 "咖啡馆"
  radius   = "1800"               // 字符串，单位米，见 2.2（下限 1000）
)
```

要点：

- **参数格式**：`location` 是 `"经度,纬度"` 的单字符串；`radius` 是字符串。`keywords` 用高德分类里常见的中文关键词，不要塞入"安静""不排队"这类高德不支持的修饰词。
- **返回值形态**：`{ "pois": [ { "id", "name", "address", "typecode" } ] }`，单次最多约 20 条。
  ⚠️ **周边搜索不返回坐标（`location`）**——实测确认返回字段只有 `id/name/address/typecode`。不同版本的高德 MCP 工具返回字段可能不一致：**如果返回里已带 `location` 可直接使用；没有就必须走 §4 的 `maps_search_detail` 补齐坐标**，否则无法做路线规划。
  ⚠️ **返回顺序不是"由近到远"**（高德默认综合排序，且此工具不返回距离字段）。**绝对不要把"列表靠前"理解成"离得近"**，也不要按列表顺序直接取前 3 个当推荐——排序必须等 §5 拿到真实步行数据后再定。
  ⚠️ **`pois` 为空数组表示"这个范围内没搜到"，不是服务故障**；只有拿到 `Around Search failed: ...` 之类文本才算调用失败。这两条分支的处理方式不同（见第 7 节），不要混淆。
- 若周边搜索无结果或关键词命中很差（明显不是用户要的类型），降级用 **`maps_text_search`**（只传 `keywords`=类型词、`city`=城市；该工具的入参校验里**没有** `citylimit`，多传可能被拒；若环境版本要求 `types` 再补 `types`=POI 类型）在同城市找，再走第 4、5 步；此时**不得**把"城市范围内的结果"说成"附近的结果"，要说明是放宽了搜索范围。
- 工具报错（如 `Around Search failed: ...`、配额超限、服务异常）按第 7 节处理，**不要凭印象补地点**。

候选选取：从返回的 `pois` 中，按 `name`/`typecode` 与需求的相关性挑出 **8 个左右**候选进入下一轮。**注意去重**：同一品牌在同一栋楼的多店（如实测中的两家"瑞幸咖啡·湖滨88"）按 `id` 是不同 POI，但对用户不是不同选择，处理规则见 §6 的"去重与多样性"。

## 4. 第三步：补齐坐标、校验类别、按直线距离剪枝（POI 详情）

对每个候选调用 **`maps_search_detail`**：

```
maps_search_detail(id = <候选的 POI id>)
```

返回 `{ id, name, location, address, business_area, city, type, alias, ...biz_ext }`，其中：

- **`location`**：地点坐标（`经度,纬度`）——§5 终点坐标的唯一来源。
- **`type`**：高德给的人类可读分类，形如 `餐饮服务;餐饮相关;咖啡厅`，**可能用 `|` 拼多个分类**（实测：`购物服务;服装鞋帽皮具店;服装鞋帽皮具店|餐饮服务;餐饮相关场所;餐饮相关`）。**只要任一分段命中即可视为类别符合**。用它校验类别是否真的符合需求：
  - 用户要"咖啡馆" → 任一分段或 `name` 命中"咖啡/coffee"等；只卖咖啡机、咖啡豆零售，或分类实为"休闲酒吧""甜品店"的，**都不算命中**，剔除。
  - 用户要"公园" → 命中"公园广场/旅游景点"类；小区绿地、商家自称"公园"不算。
  - ⚠️ **`type` 本身会被高德标错**（实测：一家真实营业的"西西弗书店&矢量咖啡"被标成 `汽车销售;汽车销售;汽车销售`）。所以**不能只看 `type` 就剔除**，要 `type` 与 `name` 二者取其一命中；但反过来，当 `type` 指向 `公司企业/工厂/政府机构/学校` 这类**不可到访的场所**、而名称又只是"××全国总部""××办公室"时，**应剔除**（实测"迷宫蓝共创书店全国总部"是公司，不是可以走进去的书店）。
  - 校验不过的要丢弃，**不要把类型不符的地点当作符合条件的推荐**（这是"数据真实性/需求满足"最常见的失分点）。
- **`address`**：回答里展示的地址用它（周边搜索的 address 可能为空或多址拼接，取详情的更完整）；若 `address` 为空数组/空串，退化为 `city` + `business_area`，并在该条说明"详细地址：高德未返回"。
  ⚠️ **地址文本里可能自带"××地铁站出入口步行420米"这类描述**（实测存在）。那是高德写的方位备注，**不是本次路线规划结果**，绝不能填进"步行距离/步行时间"列，也不要拿它和路线返回值对比。
- **`biz_ext`** 里可能带 `rating`（评分）、`cost`（人均）、`open_time`/`opentime`（营业时间）等——**只有这次调用真的返回了该字段，才能在回答里引用**，并写成"高德标注评分 4.6"这类可核对的表述。字段缺失就是缺失，写"未核实"，**不要**用常识补一个值。

**剪枝（省调用次数，必做）**：拿到坐标后，用起点与候选坐标算**直线距离**做粗排（估算即可，也可用 `maps_distance`），**只保留直线距离最近的 6 个**进入 §5。剔除标准要**宽松**：只有当直线距离已超过 `walk_limit_min × 80 × 1.5` 米（即比步行预算还大一半以上）时才直接踢掉。

> 为什么宽松：**步行路网距离并不总是大于直线距离**。实测中一家位于商场 B1 层的咖啡店，直线 62 米而高德步行只给 24 米——POI 坐标在建筑体内，路线会吸附到出入口。所以"直线看着超了"不能推出"步行一定超时"，判得太狠会误杀真正可达的地点。
> 反过来同样成立：**直线距离绝不能当作步行距离展示**，它在这里只用来决定"要不要继续查"。

调用量控制：详情调用不超过 8 次。

## 5. 第四步：算真实步行路线（步行路径规划）

对剪枝后留下的每个候选，调用 **`maps_direction_walking`**：

```
maps_direction_walking(
  origin      = origin_coord,          // 起点，"经度,纬度"
  destination = poi_detail.location    // 该候选坐标，"经度,纬度"
)
```

返回 `{ route: { origin, destination, paths: [ { distance, duration, steps: [...] } ] } }`：

- **`distance`**：步行距离，**单位米**。
- **`duration`**：步行耗时，**单位秒**。
- **判定与展示口径（全文统一）**：
  - 是否超时，用**原始秒数**判：`duration ≤ walk_limit_min × 60` 才算符合。
  - 展示给用户的分钟数用**向上取整**：`分钟 = ceil(duration / 60)`，避免"14 分 50 秒"被四舍五入写成"15 分钟"却与上限判断不一致。
  - 同一份回答里，距离与时间的换算方式不得中途改变。
- `steps[].instruction` 是分段指令，可用于一句到达提示（如"出站后沿 XX 路步行 300 米右转"），**只在有助于用户判断时才摘一句**，不要整段粘贴。

**硬性红线**：

1. 展示给用户的步行距离与时间**必须**来自 `maps_direction_walking` 的返回。
2. **禁止**用直线/球面距离估时间；**禁止**用 `maps_distance` 或搜索半径反推时间；`maps_distance` 只能作为"直线距离"补充说明，且必须标明是直线距离。
3. **禁止**用"约 5 分钟"这类没来源的口头估算。每条推荐都要能对应到一次真实调用返回的数字。
4. 路线规划失败（`Direction Walking failed: ...`、`paths` 为空）的候选：**不能列为符合条件的推荐**，可标注"路线未能核实"或直接舍弃，不得估算一个时间填上去。

调用量控制：步行路线调用不超过 6 次（即 §4 剪枝后的候选数）。**总工具调用目标 ≤ 15 次**（周边搜索 1 + 详情 ≤8 + 步行 ≤6），以便在单轮评测内稳定跑完。


## 6. 第五步：筛选、排序与成文

**筛选（按顺序）**：

1. 类别校验通过（§4）。
2. 步行耗时原始秒数 `duration` **≤** `walk_limit_min × 60`。**超时的候选不能进推荐列表**，也不能写成"稍远但值得"。
3. 有可用坐标与路线数据。

**排序**：默认按步行耗时升序；耗时相同时按步行距离升序；再相同按名称字典序，保证可复现。用户另有偏好时（"优先近一点"= 近优先；"评分高优先"= 先按 `biz_ext.rating` 降序，缺失评分的排在后面并说明）。**排序结果必须与展示的数字自洽**——列表里出现"9 分钟"排在"6 分钟"之前，就是自相矛盾。

**去重与多样性（6.x）**——用户要的是"几个不同的选择"，不是"同一家店的三个门"：

- **子部件要合并，判据要精确**。可靠信号是**名称的"末段"**（按 `-` 切最后一段）：若候选 A 的名称以候选 B 的末段开头，或 A 的地址写成"…<B 的末段>内"，则 A 是 B 内部的设施。例：`杭州西湖风景名胜区-四公园` 末段是"四公园"，于是 `四公园-三号木平台`、`四公园-四号木平台`（地址"…四公园内"）都是它的子设施，合并进"四公园"，不单独占名额。同理，名称形如"另一候选名 + `-分区/东门/休息区/负一层`"的也按子部件处理。
- ⚠️ **不要过度合并**：仅仅共享一个前缀**不算**子部件。实测中 `杭州西湖风景名胜区-三公园`、`-四公园`、`-五公园` 是湖边**各自独立的公园**（末段互不相同），把它们当成重复项合并是**错误**的。判据只看末段延续关系，不要看共同前缀。
- **同一品牌在同一栋楼/同一商场内多店，最多保留 1 家**：实测中 `瑞幸咖啡(湖滨88负一层店)` 与 `瑞幸咖啡(湖滨88店)` 同属湖滨88，对用户只是一个选择。把名额让给下一家不同品牌/不同地点的候选；**除非用户明确指定了品牌**。
- **三条尽量覆盖三个不同品牌**：同品牌不同地点（如两家分处不同商场的书店）可以接受，但优先把名额分散给不同品牌；只有当符合硬条件的候选确实不足两条时才允许同品牌占两席，并在说明里点出这一点。
- 去重后不足 `top_n` 时，按第 7 节如实少推荐，**不要**为了凑满 3 条把子部件或同品牌分店塞回来。

**取前 `top_n` 条（最多 3 条）。**

**输出格式**：先一句结论概览，再表格，最后一行说明。

```
在 <起点名称/坐标> 周边，按步行 <walk_limit_min> 分钟内可达、找 <poi_need>，共查询到 N 个候选、M 个符合条件，推荐以下 K 个（从近到远）：

| # | 地点名称 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | 某某咖啡 | 杭州市西湖区XX路XX号 | 420 米 | 6 分钟 | 三者中最近；高德分类"咖啡厅"，评分 4.6（高德返回）；位于XX商圈 |
| 2 | ... | ... | 780 米 | 10 分钟 | 高德分类"咖啡厅"，人均 38 元（高德返回）；是否安静未核实 |
| 3 | ... | ... | 1050 米 | 13 分钟 | 高德分类"咖啡厅"；营业状态未核实 |

说明：步行距离与时间来自高德步行路径规划（起点坐标 120.12,30.28）；搜索半径 1800 米仅用于粗筛。评分/人均等仅在高德返回字段时列出，未返回的标注"未核实"。
```

表格要求：

- 每行**必须**有：名称、地址、步行距离、步行时间、推荐理由——这是题目的四个必答项加理由。
- 推荐理由写**依据**（最近/次近、分类命中、评分、人均、所在商圈、类型差异），一句、克制、不吹。理由里的每个事实都要能指回某次工具返回值。
- 用户问的是"哪些是不同选择"，所以理由里可点出差异（如"三者中唯一带户外座位的，来自高德标签"），但不得引入无依据判断。

## 7. 结果不足、异常与诚实降级

先分清两种完全不同的情况，处理方式也不同：

- **A. 查询成功但没有匹配结果** = 工具正常返回、`pois` 为空数组，或候选全部因类别不符/步行超时被剔除。→ 属于"未找到"。
- **B. 查询本身失败** = 返回 `Around Search failed: …` / `Get poi detail failed: …` / `Direction Walking failed: …` 之类文本，或 `isError`、配额超限、网络异常。→ 属于"服务异常"。

- **合格结果少于 `top_n`**：就少推荐，并写清原因，例如："步行 15 分钟内只找到 2 家符合条件的咖啡馆（第 3 家直线 1.1 千米但步行需 19 分钟，超时未列入）。" 可附一句可执行的放宽建议（放宽到 20 分钟 / 扩大半径 / 换关键词）。
- **一个都没有（情况 A）**：如实说明"在 X 米搜索范围内、Y 分钟步行条件下未找到符合条件的 `<poi_need>`"，并说明实际查询了什么（关键词、半径、候选数、超时了几个）。**绝不编造地点或路线**，也不要为了凑数把类型不符/超时的塞进来。无结果用例按"是否正确处理"评分，不要因数量为 0 而心虚造假。
- **可先做一次放宽重试（情况 A）**：半径翻倍（如 1000 → 2000）、或关键词换成更通用的同义词，各试一次；仍不足则如实报告，并注明"已放宽至……仍未命中"。**注意实测现象：半径过小会让周边搜索返回空列表**，所以查空时第一反应应是"半径是不是太小/关键词太窄"，而不是"这里真的没有"。
- **工具调用失败 / 服务异常 / 配额超限（情况 B）**：明确说明哪一步失败、失败信息是什么，并给出用户下一步建议（稍后重试 / 换个更具体起点）。若部分候选已查到合格数据，可以先给出这部分，并标注"因服务异常仅完成部分查询，不代表周边全貌"。
- **信息缺失**：地址、坐标、评分、营业时间、类型等任一字段没有，就写"高德未返回/未核实"，不要用常识或推测补齐。安静程度、排队情况、是否需要预订、实际营业状态、店内环境等高德不提供的信息，一律**不写或明确标"未核实"**。
- **不得**把搜索半径、直线距离、地图目测当成"步行距离"呈现。

## 8. 输出前自检（逐条确认后再回答）

1. 起点坐标是 `经度,纬度` 且在中国合理区间内？搜索半径是否 ≥ 1000 米？
2. 每条推荐的名称、地址，是否与 `maps_search_detail` 返回一致（不是凭记忆写的）？
3. 每条的步行距离（米）与步行时间（分钟）是否**逐条**来自 `maps_direction_walking` 返回？有无混入直线距离、搜索半径，或**地址备注里的"步行420米"**？
4. 是否所有列出的条目都满足"类别正确 + 原始秒数 ≤ 上限 + 数量 ≤ 3"？超时项有没有被误列？
5. 顺序是按**真实步行数据**排的，而不是照抄周边搜索的返回顺序？排序方向与用户偏好一致，且与展示的数字自洽？
6. 三条推荐是不是**三个不同选择**？有没有把同一品牌的两家分店、或"某公园 + 某公园-木平台"这种子部件同时列进来？
7. 分钟数是否全文统一按向上取整换算（`ceil(duration/60)`）？
8. 有无任何"没有工具返回支撑"的形容词（安静、好喝、不排队、氛围佳、营业中、性价比高）？有则删除或改标"未核实"。
9. 结果不足/失败时，是否分清"查到了但没匹配"与"服务失败"两种情况，并如实说明了查询范围、失败原因与放宽建议？
10. 工具调用是否在预算内（≤ 15 次）？有无调用与本题无关的工具？
11. 回答是否简洁——表格 + 少量说明，不复述原始 JSON、不堆无关城市信息、不写多余开场白。

## 9. 工具兼容说明

评测环境统一提供高德 MCP Server 与密钥，工具名可能带不同前缀。按**语义**选择工具，优先级如下：

| 需要的能力 | 官方 MCP 工具名（`@amap/amap-maps-mcp-server`） |
| --- | --- |
| 周边搜索（主） | `maps_around_search`（`location`, `keywords`, `radius`） |
| 关键词搜索（备） | `maps_text_search`（`keywords`, `city`） |
| POI 详情 / 取坐标 | `maps_search_detail`（`id`） |
| 步行路径规划 | `maps_direction_walking`（`origin`, `destination`） |
| 地名转坐标 | `maps_geo`（`address`, `city`） |
| 坐标转地址 | `maps_regeocode`（`location`） |

- 若环境中某工具不可用，用同能力替代工具，并在回答中说明用了哪条链路。
- **不要在 Skill 文件或回答中写入、索要或回显任何 API Key**；密钥由评测环境配置。
- 不要为了"看起来更专业"去调用与本题无关的天气、骑行、驾车、打车、生成地图等工具。
